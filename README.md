# ECS Benchmark: ODE_ECS vs moecs vs odecs

moecs and odecs are pure archetype ECS (one SoA table per component signature). ODE_ECS is
relational-style (independent per-component `Table`s + `View`s that join them), plus an opt-in
true-archetype table, `Arch_Table`, for component sets that always travel together.

Tests and conclusions generated by Claude AI, no human intervention.

- ODE_ECS: https://github.com/odin-engine/ode_ecs
- moecs: https://github.com/helioscout/moecs
- odecs: https://github.com/NateTheGreatt/odecs
- Features comparison: [features.md](https://github.com/zm69/ecs_bench/blob/main/features.md) (ODE_ECS vs moecs only, not updated for `Arch_Table`)

**As of July 25, 2026.** ODE_ECS `5c5671c` → `df5a975` (adds `Arch_Table`) → `acfe11c` (fixes a
`Table`-iteration codegen bug, see Scenario 0). moecs (`ccd00f2`) and odecs (`e3ca0a5`) unchanged
upstream. All numbers are medians of 3 passes, all 27 binaries alternating within each pass, same
machine, `-o:aggressive`, tracking allocator for live-memory numbers. Absolute timings drift
between sessions — trust the ratios, always A/B back-to-back. Each library uses its idiomatic
fast path: ODE_ECS via `Table`/`View`/`Group`/`Arch_Table` `dense_slice`; moecs via an
`ARCHETYPE` system; odecs via `query`+`get_table`.

## `Arch_Table`

ODE_ECS's true-archetype table: N columns sharing **one** row index, so a row's every column
moves as a single unit (`arch_table__swap_rows`) instead of N separate `Table` swaps. Iteration
via `Arch_Iterator` or `arch_table__dense_slice` (always alignment-safe by construction).

**Trade-off: whole-row membership only** — no per-column `add_component`/`remove_component`,
only `arch_table__add_entity`/`remove_entity` for the entire row. Strict upgrade over a `Group`
when a component set is static per entity; wrong tool when entities gain/lose individual
components while alive (scenario 5).

**Guidance: mix `Arch_Table` + plain `Table`** — bundle components that always travel together
into one archetype row, leave independently-lived components as ordinary `Table`s (`ode_many_arch`
in scenario 2).

No `Arch_Table` variant in scenario 0 (1 column = a plain `Table`), scenario 4 (relations track
a single component; relations live in a separate `Relations_Table` mechanism), or scenario 5
(component sets are mutated column-by-column on live entities — exactly what `Arch_Table` can't
represent without a distinct archetype per subset and migration logic).

## Scenario 0 — Single component (1M entities, 100 frames)

`Position{x,y:f64}`, `pos.x += pos.y`. Isolates raw iteration, no multi-component lookup.

| Library | setup | ns/ent/frame | live mem |
|---------|-------|--------------|----------|
| ODE_ECS (table)      | **14.9 ms** | **0.22** | 76 MB     |
| ODE_ECS (view+iter)  | —           | 0.28     | —         |
| moecs                | 699.3 ms    | 3.17     | 168 MB    |
| odecs                | 3,372.9 ms  | 0.23     | **51 MB** |

**Codegen fix landed this session.** Raw `Table` iteration used to be *slower* (0.31 ns) than
`View`+`Iterator` and odecs — the loop read `positions.rows` as a live field access inside
`for &p in positions.rows`, so the optimizer couldn't prove `&p` doesn't alias `positions` and
reloaded the slice pointer every store (confirmed via `-build-mode:asm`, 20/20 reproducible).
Fix: `ecs.dense_slice(&positions)` returns `rows` by value into a fresh local slice, breaking the
aliasing. Now the fastest single-component path. Added as part of a unified `dense_slice` proc
group covering `Table`/`Compact_Table`/`Tiny_Table`/`Tag_Table`/`View`/`Group`. Purely additive,
12 new library lines, all 182 tests pass.

ODE_ECS ties/beats odecs on iteration and is ~14x faster than moecs; odecs keeps the leanest
memory (51 MB) but costs 3.4s to create 1M entities (~226x ODE_ECS) — every `add_entity` goes
through a variadic `..any` path with typeid→ComponentID lookups.

## Scenario 1 — Movement, 2 components (1M entities, 100 frames)

`Position{x,y:f64}` + `Velocity{x,y:f64}`, `pos += vel`.

| Library | setup | ns/ent/frame | live mem |
|---------|-------|--------------|----------|
| ODE_ECS (iterator)              | 17.3 ms     | 0.59     | 103 MB    |
| ODE_ECS (`dense_slice`, view)   | 16.7 ms     | 0.30     | 103 MB    |
| ODE_ECS (`dense_slice`, group)  | 15.3 ms     | 0.31     | 83 MB     |
| ODE_ECS (`arch_table__dense_slice`) | **13.6 ms** | **0.29** | **72 MB** |
| moecs                           | 722.9 ms    | 4.19     | 184 MB    |
| odecs                           | 6,260.8 ms  | 0.30     | 66 MB     |

`Arch_Table` leads on every column: two columns share one index (vs `Group`'s two), so setup is
one zero-init call and iteration is "read two columns," nothing to check. ~53x faster setup and
~14x faster iteration than moecs; odecs ties on iteration but takes 6.3s to set up (~460x).

## Scenario 2 — 32 component types, all on every entity (250k entities, 100 frames)

Movement touches only 2 of the 32 (identical 16-byte) types.

| Library | setup | ns/ent/frame | live mem |
|---------|-------|--------------|----------|
| ODE_ECS (view)                    | 19.4 ms    | 0.58 | 226 MB     |
| ODE_ECS (group, 2/32)             | 20.4 ms    | 0.30 | 221 MB     |
| ODE_ECS (arch, 2 arch + 30 table) | 19.7 ms    | 0.31 | **218 MB** |
| moecs                              | 98.0 ms    | 7.07 | 160 MB     |
| odecs                              | 7,010.0 ms | 0.31 | 131 MB     |

`ode_many_arch`: `Position`+`Velocity` in one `Arch_Table` row, other 30 types as separate
`Table`s the archetype never touches. Iteration ties `Group`; memory slightly leaner (one shared
index for the hot columns). Setup is a wash — all three pay for the same 30 `add_component`
calls regardless of mechanism.

## Scenario 3 — Structural churn: 10% despawn+respawn/frame + movement (100k entities, 100 frames)

| Library | ms/frame | ns/churn-op |
|---------|----------|-------------|
| ODE_ECS (iterator) | 0.540 | 27.0 |
| ODE_ECS (batch)    | 0.519 | 26.0 |
| ODE_ECS (group)    | 0.487 | 24.3 |
| ODE_ECS (arch)     | **0.288** | **14.4** |
| moecs              | 1.149 | 57.5 |
| odecs              | 1.776 | 88.8 |

`Arch_Table`'s biggest margin in the suite: **~1.7x faster than `Group`, ~1.8x faster than batch
`View`**. Whole-entity destroy+recreate is `Arch_Table`'s native operation — one
`arch_table__swap_rows` pass over a shared index, vs `Group`'s two separate `Table` swaps plus a
membership check. ~4x faster than moecs, ~6.2x faster than odecs; even ODE_ECS's slowest variant
here beats both other libraries.

## Scenario 4 — Entity relations: parent/child tree churn (100k entities)

10-ary forest (100 roots, depth ~4). Per frame (x100): 10k re-parents, 10k children-list reads,
10k ancestor walks; then 50 subtrees (5,550 entities) cascade-destroyed. ODE_ECS:
`Relations_Table`. moecs: `ChildOf`/`ParentOf` relations. odecs: flecs-style `ChildOf` pairs
with `Exclusive`+`Cascade` traits. Identical checksum across all three (x=13120122). No
`Arch_Table` variant (single-component scenario; relations are orthogonal to component storage).

| Library | setup | reparent ns/op | children ns/op | ancestor ns/hop | cascade destroy | live mem |
|---------|-------|----------------|-----------------|------------------|------------------|----------|
| ODE_ECS | **1.5 ms** | **6.2** | 17.1 | **1.3** | **0.12 ms** | **10 MB** |
| moecs   | 13.5 ms | 249.6 | **2.8** | 6.7 | 0.67 ms | 16 MB |
| odecs   | 102.5 ms | 197.3 | 2,268.8 | 5.3 | 9.66 ms | 19 MB |

ODE_ECS re-parents ~32-40x faster (flat intrusive arrays vs moecs's linear-search unlink/relink
and odecs's structural archetype move under `Exclusive`). Cascade destroy: odecs scans all
archetype signatures for dependents (9.66 ms) vs ODE_ECS's 0.12 ms. Counterpoint: moecs reads
children ~6x faster (direct slice) vs ODE_ECS's linked-list walk into a scratch buffer; odecs has
no direct children accessor at all (~133x ODE_ECS).

## Scenario 5 — Random mixed-component churn: 5 component sizes (100k entities)

`C0` 32B, `C1` 64B, `C2` 196B, `C3` 386B, `C4` 500B. 100k entities each get a random 1-5 of the 5
types; then 10k random adds, 10k random removes (1-5 components), 10k random destroys. Final
query: entities with at least `C2`,`C3`,`C4` (24,917 of 90k survivors), 3-component combine for
100 frames. Shared `scenario5_gen` package precomputes the schedule from a fixed seed — all four
programs do byte-identical work, same checksum (x=317613314). **No `Arch_Table` variant**: this
is exactly the workload it can't represent (per-column churn on live entities, not whole-row).

| Library | setup | add ns/op | remove ns/op | destroy (10k) | ns/ent/frame | live mem |
|---------|-------|-----------|---------------|----------------|--------------|----------|
| ODE_ECS (view)  | **4.3 ms** | 24.9 | 99.8 | 1.74 ms | 3.59 | 124 MB |
| ODE_ECS (group) | 5.5 ms | 36.2 | 116.1 | 1.66 ms | **1.52** | **121 MB** |
| moecs           | 24.2 ms | 46.7 | **65.2** | **0.20 ms** | 10.96 | 128 MB |
| odecs           | 2,369.0 ms | 9,920.7 | 414.4 | 2.23 ms | 1.61 | **72 MB** |

odecs's add-phase is the headline: ~9.9 µs/op, ~213-398x the others — every add/remove is an
archetype move copying every existing component (up to ~1.2 KB), the only scenario where copy
cost scales with real (non-uniform) sizes. ODE_ECS `View` vs `Group`: `Group` costs ~1.4-1.5x
more per structural op (rows up to 500B swapped across 3 tables) but iterates ~2.4x faster (no
alignment re-check).

# What the scenarios reveal

1. **SoA iteration is flat vs component-type count; moecs degrades.** ODE_ECS's iterator moves
   0.28 → 0.59 → 0.58 ns from 1→2→32 types (SoA touches only the columns iterated); `Group`/
   `Arch_Table` stay at ~0.30 ns; odecs similarly flat (0.23→0.30→0.31 ns). moecs: 3.17 → 4.19 →
   7.07 ns — AoS chunks get crowded and typeid scans grow with registered-type count.

2. **Three ways to remove `View`/`Group`/`Arch_Table` bookkeeping, each removing more than the
   last.** `View`'s dense fast path makes per-row pointer chasing vanish when alignment holds.
   `Group` enforces alignment by owning the tables, so there's nothing to detect. `Arch_Table`
   removes the second table entirely — one shared index, not two to keep in lockstep. Strict cost
   hierarchy in scenario 1: iteration 0.59→0.30→0.31→0.29 ns; memory 103→103→83→72 MB.

3. **Memory: archetype libraries win when components are universal.** odecs is leanest overall
   (51/66/131 MB in scenarios 0/1/2). `Group` and `Arch_Table` close most of the gap by dropping
   view-subscriber bookkeeping (scenario 1: 103→83→72 MB). In scenario 2, only the 2
   actually-iterated tables' overhead differs (226→221→218 MB) — the other 30 untouched tables'
   overhead is constant regardless of query mechanism.

4. **`Arch_Table` is now ODE_ECS's fastest structural-change path.** 14.4 ns/op vs `Group`'s
   24.3 and batch `View`'s 26.0 — one shared-index row swap instead of two independent swaps
   plus a membership check. Only works because scenario 3's churn is whole-entity destroy/
   recreate; per-column live churn (scenario 5) has no `Arch_Table` path by construction.

5. **Entity creation spans ~2.5 orders of magnitude.** 1M two-component entities: `Arch_Table`
   13.6 ms, `Group`/`View` 15.3-17.3 ms, moecs 723 ms, odecs 6,261 ms. odecs's variadic `..any`
   `add_entity` builds a temp-allocator component-ID array+map per call — the single biggest gap
   between these libraries.

6. **Groups/Arch_Tables enforce what Views merely detect — and it's a net win, not just a
   cost-shift.** Paying more on structural change for a flat iteration floor is the textbook
   EnTT full-owning-group trade, but here `Group` setup and churn both *undercut* plain `View`
   too (a `View`'s pointer-record fallback isn't free even when unused). `Arch_Table` goes
   further, removing the second `Table` a `Group` still coordinates. This would reverse only for
   a component set whose membership toggles far more often than it's swept — none of scenarios
   1-3 exercise that, and scenario 5 is precisely where per-column churn is common enough that
   neither `Group` nor `Arch_Table` is even a candidate.

# Overall

On **iteration**, SoA libraries (odecs, ODE_ECS's `Group`/`Arch_Table`) converge on the same
sub-nanosecond floor regardless of component-type count; moecs's AoS chunks degrade as types
accumulate. On **structural operations**, ODE_ECS was already fastest; `Arch_Table` widens that
further for its target shape (fixed component set, no independent per-column lifetime): ~53x
faster setup and ~4-6x faster churn than moecs/odecs, cutting ODE_ECS's own prior best (`Group`)
by roughly a third to a half. The trade is architectural: whole-row-only membership buys that
speed and is exactly why it's wrong for scenario 5's per-column churn, where `View`/`Group`
(independent `Table`s, no migration) and the archetype-migration libraries (moecs, odecs — their
home turf) remain the only options.

**Guidance:** reach for `Arch_Table` when a component set is fixed for an entity's whole
lifetime and iterated every frame (movement, render-visible components). Keep sparse-dense
`Table`s + `View`/`Group` for anything with independent per-component churn. Mix both, as
`ode_many_arch` does, when a database has both kinds of components at once.

- All workloads checksum-verified across libraries. `ode_one` reports x=400 (runs the 100 frames

  x=13120122, destroy exactly 5,550 entities. Churn programs report x=10 except moecs_churn

  — its intended usage (per-call scratch allocation), not overhead added by the benchmark.
- Movement is ODE_ECS's home turf; moecs does more per-frame bookkeeping by design (deferred
  actions, archetype re-filtering) for features not exercised here.
