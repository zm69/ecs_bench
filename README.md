# ECS Benchmark: ODE_ECS vs moecs vs odecs

moecs and odecs are pure archetype ECS (one SoA table per component signature). ODE_ECS is
relational-style (independent per-component `Table`s + `View`s that join them), plus an opt-in
true-archetype table, `Arch_Table`, for component sets that always travel together.

Tests and conclusions generated by Claude AI, no human intervention.

- ODE_ECS: https://github.com/odin-engine/ode_ecs
- moecs: https://github.com/helioscout/moecs
- odecs: https://github.com/NateTheGreatt/odecs
- Features comparison: [features.md](https://github.com/zm69/ecs_bench/blob/main/features.md)

**As of August 15, 2026.** ODE_ECS `acfe11c` (last refresh) → `cafc8b8` (today's HEAD, unchanged
since the previous run). moecs (`ccd00f2`) and odecs (`e3ca0a5`) unchanged upstream. Numbers below
are medians of a *third* fresh 3-pass run today (all 28 binaries alternating within each pass,
same machine, `-o:aggressive`, tracking allocator for live-memory numbers, no rebuild — source
identical to the prior run). Running the full suite twice back-to-back on the same binaries turned
out to be informative in its own right: it's the actual noise floor, not an estimate of one. Most
scenarios landed within a few percent of the previous run and of each other's 3 in-run passes.
Scenario 5 did not — its `add`/`remove` ns/op medians moved 15-25% between the two full runs, more
than the spread between different ODE_ECS variants *within* either run. That scenario's per-op
numbers are called out as noisy where they matter below; treat single-digit-percent differences
there as unreliable regardless of which run they're read from. Memory deltas don't have this
problem — allocator byte counts are deterministic, not timed — so they remain the reliable
cross-session signal. Each library uses its idiomatic fast path: ODE_ECS via
`Table`/`View`/`Group`/`Arch_Table` `dense_slice`; moecs via an `ARCHETYPE` system; odecs via
`query`+`get_table`.

## What's new in ODE_ECS since the last refresh (`acfe11c` → `cafc8b8`)

- **Fixed a broken build.** ODE_ECS moved from `G:\odin\ode_ecs` to `G:\odin\ode\ode_ecs` between
  sessions; all 14 `ode_*` benchmark binaries here still imported the old path and didn't compile.
  Repointed every import to `../../ode/ode_ecs`.
- **`entity_id`'s generation field grew (16-bit → 32-bit).** Shows up as a consistent, deterministic
  live-memory increase across every ODE_ECS variant this session vs. the last refresh — roughly
  +15 bytes/entity (e.g. scenario 1: 103→118 MB at 1M entities; scenario 4: 10→12 MB at 100k). This
  is the one cross-session number in this doc treated as a real signal rather than noise, since
  memory isn't subject to timing jitter the way wall-clock numbers are.
- **New: `enable_component`/`disable_component`** — a soft, bitset-based toggle that excludes a
  component from `View` matching without moving or losing its stored data, the opposite of
  `add_component`/`remove_component`'s real structural tail-swap. Benchmarked below as a new
  scenario 5 variant, `ode_mixed_enable` — see that section for the (non-obvious) result.
- **New: View `any_of`** — an OR combinator completing `includes` (AND)/`excludes` (NOT). Query
  expressiveness, not benchmarked separately here (no iteration-speed claim attached to it in the
  docs).
- Internal-only changes not separately benchmarked: an `Arch_Table` micro-optimization, lazy
  allocation of subscriber/sync-watcher bookkeeping, and a fix that skips the
  disabled-components bitset check on `View` matching entirely for databases that never call
  `disable_component` (so the churn/view numbers below for the non-enable variants aren't paying
  a tax for a feature they don't use).

## `Arch_Table`

ODE_ECS's true-archetype table: N columns sharing **one** row index, so a row's every column
moves as a single unit (`arch_table__swap_rows`) instead of N separate `Table` swaps. Iteration
via `Arch_Iterator` or `arch_table__dense_slice` (always alignment-safe by construction).

**Trade-off: whole-row membership only** — no per-column `add_component`/`remove_component`,
only `arch_table__add_entity`/`remove_entity` for the entire row. Strict upgrade over a `Group`
when a component set is static per entity; wrong tool when entities gain/lose individual
components while alive (scenario 5).

**Guidance: mix `Arch_Table` + plain `Table`** — bundle components that always travel together
into one archetype row, leave independently-lived components as ordinary `Table`s (`ode_many_arch`
in scenario 2).

No `Arch_Table` variant in scenario 0 (1 column = a plain `Table`), scenario 4 (relations track
a single component; relations live in a separate `Relations_Table` mechanism), or scenario 5
(component sets are mutated column-by-column on live entities — exactly what `Arch_Table` can't
represent without a distinct archetype per subset and migration logic).

## Component `enable_component`/`disable_component`

A soft toggle: exclude a component from `View` matching without a structural move (no tail-swap,
no re-zero, data untouched). Docs frame it as the low-cost alternative to `remove_component`/
`add_component` when a component's *presence* needs to flip often but its *data* should survive
the flip. Benchmarked below in scenario 5 (`ode_mixed_enable`) against the structural `View`/
`Group` variants — the result is more interesting than "it's just faster."

## Scenario 0 — Single component (1M entities, 100 frames)

`Position{x,y:f64}`, `pos.x += pos.y`. Isolates raw iteration, no multi-component lookup.
Both rows below come from one binary (`ode_one`) sharing a single setup phase.

| Library | setup | ns/ent/frame | live mem |
|---------|-------|--------------|----------|
| ODE_ECS (table)      | **16.5 ms** | **0.22** | 91 MB     |
| ODE_ECS (view+iter)  | —           | 0.29     | —         |
| moecs                | 718.1 ms    | 4.44     | 168 MB    |
| odecs                | 6,408.8 ms  | 0.31     | **51 MB** |

ODE_ECS's raw `Table` `dense_slice` path is the fastest single-component path this run, edging
past odecs (0.22 vs 0.31 ns) and ~20x faster than moecs. odecs keeps the leanest memory (51 MB)
but costs 6.4s to create 1M entities (~388x ODE_ECS) — every `add_entity` goes through a variadic
`..any` path with typeid→ComponentID lookups.

## Scenario 1 — Movement, 2 components (1M entities, 100 frames)

`Position{x,y:f64}` + `Velocity{x,y:f64}`, `pos += vel`.

| Library | setup | ns/ent/frame | live mem |
|---------|-------|--------------|----------|
| ODE_ECS (iterator)              | 18.3 ms     | 0.60     | 118 MB    |
| ODE_ECS (`dense_slice`, view)   | 18.3 ms     | 0.30     | 118 MB    |
| ODE_ECS (`dense_slice`, group)  | 16.5 ms     | 0.32     | 99 MB     |
| ODE_ECS (`arch_table__dense_slice`) | **14.2 ms** | **0.31** | **87 MB** |
| moecs                           | 718.1 ms    | 4.44     | 184 MB    |

`Arch_Table` leads on setup: two columns share one index (vs `Group`'s two), so it's one

each) but takes 6.4s to set up (~451x).

## Scenario 3 — Structural churn: 10% despawn+respawn/frame + movement (100k entities, 100 frames)

| Library | ms/frame | ns/churn-op |
|---------|----------|-------------|
| ODE_ECS (iterator) | 0.506 | 25.3 |
| ODE_ECS (batch)    | 0.484 | 24.2 |
| ODE_ECS (group)    | 0.453 | 22.6 |
| ODE_ECS (arch)     | **0.289** | **14.5** |
| moecs              | 1.049 | 52.5 |
| odecs              | 1.939 | 96.9 |

`Arch_Table`'s biggest margin in the suite: **~1.6x faster than `Group`, ~1.7x faster than batch
`View`** — both figures reproduced almost exactly from the previous run. Whole-entity
destroy+recreate is `Arch_Table`'s native operation — one `arch_table__swap_rows` pass over a
shared index, vs `Group`'s two separate `Table` swaps plus a membership check. ~3.6x faster than
moecs, ~6.7x faster than odecs; even ODE_ECS's slowest variant here beats both other libraries.

## Scenario 4 — Entity relations: parent/child tree churn (100k entities)

10-ary forest (100 roots, depth ~4). Per frame (x100): 10k re-parents, 10k children-list reads,
10k ancestor walks; then 50 subtrees (5,550 entities) cascade-destroyed. ODE_ECS:
`Relations_Table`. moecs: `ChildOf`/`ParentOf` relations. odecs: flecs-style `ChildOf` pairs
with `Exclusive`+`Cascade` traits. Identical checksum across all three (x=13120122). No
`Arch_Table` variant (single-component scenario; relations are orthogonal to component storage).

| Library | setup | reparent ns/op | children ns/op | ancestor ns/hop | cascade destroy | live mem |
|---------|-------|----------------|-----------------|------------------|------------------|----------|
| ODE_ECS | **1.5 ms** | **5.0** | 17.1 | **1.2** | **0.13 ms** | **12 MB** |
| moecs   | 13.5 ms | 253.0 | **2.9** | 8.5 | 0.69 ms | 16 MB |
| odecs   | 107.7 ms | 208.4 | 2,338.9 | 5.6 | 9.55 ms | 18 MB |

ODE_ECS re-parents ~42-51x faster (flat intrusive arrays vs moecs's linear-search unlink/relink
and odecs's structural archetype move under `Exclusive`). Cascade destroy: odecs scans all
archetype signatures for dependents (9.55 ms) vs ODE_ECS's 0.13 ms (~73x, though this scenario's
cascade number is only 5,550 total ops — noisier than the other columns; the previous run put it
at 0.19 ms/~55x). Counterpoint: moecs reads children ~6x faster (direct slice) vs ODE_ECS's
linked-list walk into a scratch buffer; odecs has no direct children accessor at all (~137x
ODE_ECS).

## Scenario 5 — Random mixed-component churn: 5 component sizes (100k entities)

`C0` 32B, `C1` 64B, `C2` 196B, `C3` 386B, `C4` 500B. 100k entities each get a random 1-5 of the 5
types; then 10k random adds, 10k random removes (1-5 components), 10k random destroys. Final
query: entities with at least `C2`,`C3`,`C4` (24,917 of 90k survivors), 3-component combine for
100 frames. Shared `scenario5_gen` package precomputes the schedule from a fixed seed — all
programs do byte-identical work. **No `Arch_Table` variant**: this is exactly the workload it
can't represent (per-column churn on live entities, not whole-row).

| Library | setup | add ns/op | remove ns/op | destroy (10k) | ns/ent/frame | live mem |
|---------|-------|-----------|---------------|----------------|--------------|----------|
| ODE_ECS (view)             | **4.2 ms** | 33.8 | 111.0 | 1.91 ms | **3.90** | 126 MB |
| ODE_ECS (group)            | 5.5 ms | 38.7 | 123.7 | 1.99 ms | 1.66 | **123 MB** |
| ODE_ECS (enable/disable)   | 6.6 ms | 33.4 | **63.4** | 3.38 ms | 4.12 | 126 MB |
| moecs                      | 25.5 ms | 66.3 | 84.5 | **0.33 ms** | 11.52 | 128 MB |
| odecs                      | 2,455.6 ms | 10,132.5 | 484.4 | 2.54 ms | 1.77 | **72 MB** |

odecs's add-phase is the headline: ~10.1 µs/op, ~150-300x the others — every add/remove is an
archetype move copying every existing component (up to ~1.2 KB), the only scenario where copy
cost scales with real (non-uniform) sizes. This scenario's `add`/`remove` ns/op numbers moved
15-25% between this run and the previous one for *every* ODE_ECS/moecs variant (odecs, working
with much larger absolute costs, stayed proportionally stable) — see the noise note at the top.
Read the `View`-vs-`Group` structural-op gap directionally, not as a fixed multiplier: this run
puts `Group` only ~1.1x over `View` on both add and remove; the previous run had it at ~1.5x. The
iterate-side comparison held up better across both runs — `View` is consistently ~2.2-2.4x slower
per entity than `Group` (no alignment re-check needed once `Group` enforces it).

### `enable_component`/`disable_component` vs structural add/remove (`ode_mixed_enable`)

Same workload, same op counts, same final view membership (matched=24,917 either way, verified
identical to the `view`/`group` variants) — but `ode_mixed_enable` adds all 5 components to every
entity up front, then uses the *initial* random mask to `disable_component` the ones a real
entity "doesn't have," and the add/remove phases become `enable_component`/`disable_component`
guarded by `is_component_disabled` instead of `has_component` + a real `add_component`/
`remove_component`.

Ran this twice now (two independent fresh 3-pass sessions, same day). What holds up and what
doesn't is itself the finding:

1. **`disable`/`remove` — directionally consistent, magnitude noisy.** `disable_component` beat
   structural `remove_component` on `View` in both runs (63.4 ns vs 111.0 ns this run, ~1.75x;
   94.3 ns vs 134.0 ns last run, ~1.4x). Same direction, different multiplier — trust "disable
   is meaningfully cheaper than a real remove here," not any specific ratio.
2. **`enable`/`add` — no reliable winner, and the previous run's specific claim doesn't hold up.**
   Last run had `enable_component` (46.4 ns) slower than structural `add_component` on `View`
   (41.1 ns) and concluded enable "isn't a speed win" on the add side. This run they're
   statistically tied (33.4 ns vs 33.8 ns — enable marginally *ahead*, by less than this
   scenario's own run-to-run swing). The honest read: `add`/`enable` cost is in the same tier as
   structural `add_component`, full stop — which run "wins" isn't a reproducible signal at these
   component sizes (32-500 bytes). `docs/view.md` prices `disable_component` at "one bitset test
   against a per-entity bitset... same cost as `excludes`/`any_of`" — but a real
   `add_component`/`remove_component` pays the same view-matching bitset test as part of its own
   subscriber-notification walk, so the *data copy* is the only cost `enable_component` actually
   saves, and at these sizes that copy is small next to the notification walk either way.
3. **It doesn't cost extra memory, and this one isn't noisy — it's structural.** A naive worry
   going in: pre-adding all 5 components to every entity (required, since `enable`/`disable` can
   only toggle a component that already has a physical slot) should cost more live memory than the
   original mask-driven partial add. It doesn't, in either run — both variants report 126 MB,
   because `ecs.Table(T)` preallocates its full `cap` (`N` = 100k rows here) up front regardless of
   how many rows are actually populated; the mask only changes which slots are logically "live,"
   not how much backing storage each of the 5 tables reserves. This is a property of `Table`'s
   preallocation model, not a timing measurement, so it doesn't share the noise problem above.
4. **Iteration is consistently slower per entity than the structural `View` variant** — 4.12 vs
   3.90 ns/ent/frame this run (~6%), 4.22 vs 3.53 last run (~20%). Direction reproduced twice;
   magnitude didn't. Still not root-caused — plausibly a physical row-ordering effect (every table
   holds a full 100k-row spread with matched/unmatched rows interleaved by insertion order, vs the
   structural variant's smaller, more mask-correlated tables) — flagged as an open question, not
   an explained result, in both runs.

Bottom line, now backed by two runs instead of one: reach for `enable_component`/
`disable_component` when you need a component's *visibility* to flip without ever losing or
reallocating its *data* (e.g., "stunned" excluding a unit from an AI view while keeping its stats
intact for a UI to read) — that's a correctness/API-ergonomics win `add_component`/
`remove_component` can't give you at all, not a raw-throughput one. `disable` reproducibly beats a
structural `remove` here; `enable` vs structural `add` is a wash, not a win, at these component
sizes — don't reach for this feature expecting a speedup on the add side.

# What the scenarios reveal

1. **SoA iteration is roughly flat vs component-type count; moecs degrades.** ODE_ECS's
   View+`Iterator` path moves 0.29 → 0.60 → 0.59 ns from 1→2→32 types (SoA touches only the
   columns iterated, most of the jump is 1→2); `Group`/`Arch_Table` stay at ~0.31-0.32 ns; odecs
   similarly close to flat (0.31→0.31→0.32 ns). moecs: 4.44 → 4.44 → 7.47 ns — AoS chunks get
   crowded and typeid scans grow with registered-type count.

2. **Three ways to remove `View`/`Group`/`Arch_Table` bookkeeping, each removing more than the
   last.** `View`'s dense fast path makes per-row pointer chasing vanish when alignment holds.
   `Group` enforces alignment by owning the tables, so there's nothing to detect. `Arch_Table`
   removes the second table entirely — one shared index, not two to keep in lockstep. Cost
   hierarchy in scenario 1: iteration 0.60→0.30→0.32→0.31 ns; memory 118→118→99→87 MB.

3. **Memory: archetype libraries win when components are universal.** odecs is leanest overall
   (51/66/131 MB in scenarios 0/1/2, unchanged from the last refresh — a useful cross-session
   sanity check since its source didn't change either). `Group` and `Arch_Table` close most of the
   gap by dropping view-subscriber bookkeeping (scenario 1: 118→99→87 MB). In scenario 2, only the
   2 actually-iterated tables' overhead differs (229→225→222 MB) — the other 30 untouched tables'
   overhead is constant regardless of query mechanism.

4. **`Arch_Table` is still ODE_ECS's fastest structural-change path.** 14.5 ns/op vs `Group`'s
   22.6 and batch `View`'s 24.2 — one shared-index row swap instead of two independent swaps plus
   a membership check. Only works because scenario 3's churn is whole-entity destroy/recreate;
   per-column live churn (scenario 5) has no `Arch_Table` path by construction, and —
   `enable_component`/`disable_component` isn't a substitute for it either (it toggles visibility,
   not physical presence, so it still needs the component's slot to already exist).

5. **Entity creation spans ~2.5 orders of magnitude.** 1M two-component entities: `Arch_Table`
   14.2 ms, `Group`/iterator/dense-view 16.5-18.3 ms, moecs 718.1 ms, odecs 6,408.8 ms. odecs's
   variadic `..any` `add_entity` builds a temp-allocator component-ID array+map per call — the
   single biggest gap between these libraries.

6. **Groups/Arch_Tables enforce what Views merely detect — and it's a net win, not just a
   cost-shift.** Paying more on structural change for a flat iteration floor is the textbook
   EnTT full-owning-group trade, but here `Group` setup and churn both *undercut* plain `View`
   too (a `View`'s pointer-record fallback isn't free even when unused). `Arch_Table` goes
   further, removing the second `Table` a `Group` still coordinates. `enable_component`/
   `disable_component` is a fourth, orthogonal tool for the specific case scenario 5 represents
   (arbitrary per-entity component churn) — but as measured across two runs above, it earns its
   keep on API semantics (data survives the toggle) rather than on raw ns/op, and its own ns/op
   numbers were the noisiest in the whole suite.

# Overall

On **iteration**, SoA libraries (odecs, ODE_ECS's `Group`/`Arch_Table`) converge on the same
sub-nanosecond floor regardless of component-type count; moecs's AoS chunks degrade as types
accumulate. On **structural operations**, ODE_ECS was already fastest; `Arch_Table` widens that
further for its target shape (fixed component set, no independent per-column lifetime): ~51x
faster setup and ~3.6-6.7x faster churn than moecs/odecs, cutting ODE_ECS's own prior best (`Group`)
by roughly a third. The trade is architectural: whole-row-only membership buys that speed and is
exactly why it's wrong for scenario 5's per-column churn, where `View`/`Group` (independent
`Table`s, no migration), the new `enable_component`/`disable_component` soft toggle (visibility
without physical migration, but no faster in raw terms at these sizes), and the
archetype-migration libraries (moecs, odecs — their home turf) are the options.

**Guidance:** reach for `Arch_Table` when a component set is fixed for an entity's whole
lifetime and iterated every frame (movement, render-visible components). Keep sparse-dense
`Table`s + `View`/`Group` for anything with independent per-component churn; reach specifically
for `enable_component`/`disable_component` within that when a component needs to disappear from
queries *without losing its data* (not for raw toggle throughput). Mix `Arch_Table` + plain
`Table`s, as `ode_many_arch` does, when a database has both kinds of components at once.

  x=13120122, destroy exactly 5,550 entities. Churn programs report x=10 except moecs_churn

- odecs benchmarks call `free_all(context.temp_allocator)` once per frame outside timed sections
  — its intended usage (per-call scratch allocation), not overhead added by the benchmark.
- Movement is ODE_ECS's home turf; moecs does more per-frame bookkeeping by design (deferred
  actions, archetype re-filtering) for features not exercised here.
